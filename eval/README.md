# 評価キット（P20・2026-10-14）

Gemini の無料枠のモデルは予告なく入れ替わる。新しいモデルに乗り換える前に、**同じ物差しで測る**ための道具。
選ぶ基準の最優先は **「読めない箇所を黄で申告するか」**（台帳 P7-c）。「毎日の見張り」や、有料枠・他社のモデルを比べるときにも使う。

## 使い方（リポジトリの直下で・Node の標準機能だけ）

```
node eval/run.mts                                  # 本番の試験済み＋緊急用（lib/gemini.ts の MODEL_TIERS）を 3件×3回
node eval/run.mts --models gemini:gemini-3.7-flash --runs 2
node eval/run.mts --cases hard --runs 1            # 1件だけ
node eval/run.mts --dry                            # API を呼ばずに組み立てだけ確かめる
node eval/run.mts --models gemini:gemini-3.5-flash-lite --variant B   # プロンプトの案を試す（評価の中だけ・P25）
```

- 鍵は `.env.local` の **`GEMINI_EVAL_API_KEY`（評価用・本番と別のプロジェクトで作った鍵）だけ**（P23）。値は表示も保存もしない。
  - 無い・本番の鍵（`GEMINI_API_KEY`）と同じ値なら、1回も呼ばずに止まる（P22 で評価が本番の1日の枠を使い切ったため）。
  - ⚠️ 無料枠の上限は**プロジェクトごと**（2026-10-14 は約10回/モデル/日。失敗した呼び出しも数える）。本番と同じプロジェクトの鍵は、値が違っても本番の枠を食う。
  - 置き方: Google AI Studio で**新しいプロジェクト**を選んで鍵を作り、`.env.local` に `GEMINI_EVAL_API_KEY=…` の1行を足す（値はコミットしない）。
- 失敗しても再試行しない。429（枠切れ）が出たらそのモデルは止める。503（混雑）が2回続いても止める。
- 結果は `docs/eval/YYYY-MM-DD-HHMM.md`（表）と `.json`（各回の採点と変換の結果）。画像と鍵は残さない。

## 毎日の見張り（P23・`eval/watch.mts`）

GitHub Actions（`.github/workflows/watch.yml`）が**毎日 22:00（日本時間）に1回**動く。手で動かすときは Actions の画面の「Run workflow」。

- 鍵は GitHub の secrets の `GEMINI_EVAL_API_KEY` だけ。**未登録なら何もせず成功で終わる**（失敗の通知を出さない）。
- 評価用の鍵でモデルの一覧を引いて前回と比べ、試験済み・緊急用の各モデルで評価用のメモ1件（`hard`）を1回だけ変換する。
- Issue を立てる（同じ題が開いていれば立てない）: 試験済みが一覧から消えた／課金が要る／使えない／変換に失敗した／3晩続けて混雑／新しい Flash 系のモデルが出た（評価キットを 3件×1回 走らせた表を付ける）。
- 記録は `watch-log` ブランチ（main とは別の、記録だけの枝）: `state.json`（前回の一覧・続けて混雑した日数）・`congestion.md`（時刻・モデル・結果）・`eval/`（新しいモデルの評価結果）。
- 手元で: `node eval/watch.mts --state <置き場所>`（GitHub の変数が無ければ Issue は立てず、題を表示するだけ）。
- ⚠️ 公開リポジトリの定期実行は、リポジトリに60日間動きが無いと GitHub が止める（Actions の画面から再開できる）。

## 何を測るか

| 列 | 中身 |
|---|---|
| 要点の一致率 | 正解の要点（言い換えの候補つき）が1つの項目の中に出たか。読みにくくした箇所は除く（`eval/score.ts`） |
| 振り分け | 読めた要点のうち、正解の項目に入った割合（合否には入れない） |
| 黄（件） | 黄の印の数 |
| 黄∩印 | 読みにくくした箇所（印）のうち、黄で申告された数 |
| 申告なし | 印の箇所を黄・青なしで誤読・欠落させた数（正しく読めたものは数えない）。**「〇〇」と書いたもの**（塗りつぶしと同じ扱いにした。黄にならず要確認の数に出ない）も数え、内訳に出す（P25） |
| 作り話 | 正解に無い数を申告なしで書いた・塗った名前を書いた・正解側に挙げた作り話の語が出た |
| 〇〇 | 塗った箇所の前後に「〇〇」があるか |
| 時間・失敗 | 1回の時間（成功のみ）・失敗の HTTP ステータス |

合否の目安は `eval/criteria.ts` の1か所（作り話0・申告なし0・**黄が、正しく読めなかった印の半分以上**（P25）・要点85%以上・〇〇すべて）。

印の判定の順は 黄 → 正読 → 青 → 〇〇 → 申告なし → 抜け（P25）。青に数えるのは語の大きさの青だけ（15字まで・行や「・」を含まない・印の前後の語を含まない）。
文まるごとの青（「誰の話か」「どの項目か」の推定）は、印の語の申告ではないので数えない。

⚠️ 印のうち「週1〜2」（にじんでいるのは前の「飲み忘れ 週」）・「12,000円」・「10/3」・「2kg」・「10/10」は、拡大すると形がたどれて読める（P25 で確かめた）。
本当に読めないのは「眠剤」「訪看」「半分」「10分」。

## プロンプトの案（P25・`eval/prompt-variants.ts`）

本番のプロンプト（`lib/prompt.ts`）は変えずに、規則4の "y" の説明の後ろへ文を足して試す（`--variant A` / `--variant B`）。
結果の表と json に案の名前とプロンプトの指紋が残る。案は2つまで。本番に入れるかは設計側が決める。

## 本番と同じ経路

プロンプト＝`lib/prompt.ts` の `buildPrompt`（辞書は空）／呼び出し＝`lib/gemini.ts` の `callModel`（本番の `generateWithFallback` が使う1回の呼び出し・temperature 0）／
返答の読み取りと人名の機械検出＝`lib/convert-core.ts` の `finishConversion`（変換API と同じ）。画像はアプリが送る形（JPEG 0.92・`eval/make-inputs.py`）。

## 提供元を足す（今回は足していない）

`eval/providers.ts` に1件足し、鍵を `.env.local` に置く。モデルは「提供元:モデル名」で指定する。
Gemini の有料枠は呼び方が同じで鍵だけ違う。他社は「プロンプトと画像を送り、返答の本文を返す」関数を書けば、後処理と採点はそのまま使える。
⚠️ 評価で測れることと、本番で使えること（その社の規約・規程整理）は別。
